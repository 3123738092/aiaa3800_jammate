# JamMate Renderer 与 Runtime 验收

以本地 `integration/mrt2-demo` 的工作树为验收对象，沿用 InputEvent、JamState、BandPlan 和浏览器小节调度。真实模型为 MRT2 Small、magenta-rt 2.0.3、MLX 0.31.2、官方 MLXfn 导出，运行于 macOS 15 Apple Silicon。模型实验记录了基线 Git HEAD、工作树状态、实际条件及逐帧耗时。模型输出统一保存为 48 kHz 双声道 PCM16。真人听感评分保留在每个用例的 `listening` 字段。

## A · 文字与条件

独立模型跑了 A01–A08，每项两次，每次 10 秒。每个用例的两次 WAV 哈希一致，八种措辞产物的哈希各异。该 MLXfn 导出使用固定采样行为，复跑反映可重复性。16 次输出均无满幅削波，推理 RTF 约 0.59–0.71。Bossa Nova 英文短句的 RMS 约 0.055，中文短句约 0.111。响度差异可以影响盲听，应在等响条件下分别评价语言、措辞和自然度。

系统路径用四条中英原话打开实际 Jam 会话，保存 InputEvent、JamState、开场 BandPlan、实际提交的 MusicCoCa 文本和 token。四组 A–E 共完成 20 个 5 秒样本，分别使用简短英文、系统文本、稀疏和弦、核心旋律与节奏、完整音符条件。C–E 在同一 96 BPM、C 大调模板上改变条件数量，B–E 使用同一个实际系统 Prompt。WAV、帧条件和结果保存在 `system-ablation-verified/`。

在中文 Bossa 路径，A–E 的 RMS 依次为 0.054、0.071、0.011、0.018、0.040。中文 Rock 路径依次为 0.116、0.057、0.041、0.093、0.064。C 的音高占用为 144 个格，E 为 504 个格，同帧最大音高数从 3 增至 8。加条件会明显改变输出，响度变化随风格和条件组合而异。主观清晰度、音色和杂音成因需对这些配对音频做等响复核。

Adapter 对常见风格词做有限的中英规范化，保留其余用户描述。开场 BPM、调性由当前 BandPlan 状态提供，避免后续改调或调速时与开场原话重复。生成所用的实际文本与 token 可从 Jam 调试 API 查看。

## B · WAV、M4A 与哼唱

`model/fixtures/` 包含两份 96 BPM、4/4、C 大调的合成 Motif 和标准 MIDI，以及拍手、静音与低幅噪声。Motif B 包含连续同音、长短音和休止。固定素材由脚本生成。

| 路径 | 本轮合成 Motif B 的结果 |
| --- | --- |
| B01 文字 | Bossa Nova 基准，RMS 约 0.055 |
| B02 Audio | WAV 进入 MusicCoCa，12 个风格 token 均与文字基准不同，输出接近静音 |
| B03 自动 MIDI | 经 JamMate 哼唱分析及 MIDI 导出，输出 RMS 约 0.008 |
| B04 矫正 MIDI | 脚本接受经过独立复核的 MIDI。本轮保留未测结果 |
| B05 标准 MIDI | 使用标准 Motif B，输出 RMS 约 0.014 |
| B06 Audio + MIDI | 同时使用音频风格和 MIDI 网格，输出 RMS 小于 0.001 |

同一合成源的 WAV 为 40,000 帧，M4A 解码后为 40,960 帧，均为 16 kHz 单声道。两者的 12 个风格 token 与模型 WAV 哈希完全相同。Chrome 正常上传两种文件后也都得到 2.5 秒、E4–G4–A4 三个识别音和完全相同的 MRT2 文本 token。源 Motif 的两个连续 E4 合成音被当前 pYIN 合并，这是这一用例中已确认的转录损失。网页走解码和哼唱识别，现有 MRT2 路径消费识别结果。独立 Audio Conditioning 通过 `embed_style(Waveform)` 进入 MusicCoCa。文字和参考音频共享风格条件槽，音高和鼓点可独立提供。

本轮新生成的 A01/A05 WAV 作 H05/H06 风格参考时，独立输出 RMS 分别为 0.048 和 0.090。在同一 S2 模型状态下，10 秒处从 Bossa 文字切到 Rock WAV，实测 T0 到 T3 约 1.85 秒。生成音乐参考与短合成哼唱的结果差异明显。数据保存在 `wav-references-verified/`。需要精确 Motif 时，继续使用 MIDI 或其他显式音符。原先团队的历史优质 WAV 和授权真人样本仍待复核。

## C · 声音路径和切换

用实际 A01 WAV 在 Chromium 的同采样率 Web Audio 中解码并渲染。PCM 最大绝对差约 0.0000122，小于一个 PCM16 量化单位。该条件下的 WAV 播放链路没有观察到显著数值失真。

在可分离双通道测试信号中，原硬切和修改后的互斥渐变都测到零重叠帧。原硬切最大采样跃变约 0.40，修改后约 0.00104。自动试听使用分时 8 ms 增益过渡，WAV 导出复用同一增益调度。手动试听启动时立即压掉伴奏。未开始的替代片段会随新指令失效，已经开始的片段可以继续，直到新计划实际接入或用户停止。

当前推荐按场景选路。强调精确节拍、调性和声部的交互使用规则谱与 MIDI/合成输出。强调生成音色和整体氛围的交互使用 MRT2 单独输出。独立试听可在确定的边界交替接管，预览生成等待或失败时继续播放实时伴奏。完整伴奏的并行分层仍需要相位、和声和声部隔离证据。

## D · 生成和播放时序

S0 为一次生成完整片段，S1 为每 10 秒重置模型状态后拼接，S2 为同一模型状态持续出帧并更新条件。Bossa Nova 与 Hard Rock 的 S0 各生成 10、30、60 秒，两个 S1 各生成 60 秒。静态实测 RTF 约 0.59–0.61。Bossa S2 在同一状态下完成风格、哼唱参考、密度和调性条件更新，生成 60 秒后执行停止。该轮 RTF 约 0.65，有 20 个 40 ms 截止时间超出的模型帧。

实验中的 T0 是提交既定测试输入的时刻，T2 为条件编码完成后准备交给模型，T3 为新条件首帧返回。独立 Bossa S2 里，文本更新从 T0 到 T3 约 0.37–0.44 秒，合成音频更新约 2.38 秒。Rock S2 也实跑了换 Riff 参考、加重鼓、恢复与停止，生成 40 秒，文本更新约 0.42–0.50 秒。S0/S1 已完成静态长度和拼接对照。浏览器另记录 Web Audio 起拍、缓冲重接和 HTTP 延迟。声卡传出、完整交互模式的同时间线对照及听感变化仍需继续测量。

## E · 固定指令和局部控制

第一轮连贯会话中，E07 在上一轮鼓渐强时拒绝了新排程，原因为新编排会改变已排程的保护声部。E08 的完整换调表达也被本地规则拒绝。最终在实际开启键盘、吉他和弦乐的会话里，E07 第 5 小节完成局部混音，E08 第 6 小节切到 D 大调，E13 与 E14 在保留伴奏时排入新 Riff 和变奏。E06–E16 中十条获得播放回执，E10 保持演奏并保留能力未覆盖的反馈。E01–E05 的真实 MRT2 开场均保存了 PCM，乡村开场的调度为 89 BPM，合成哼唱与合成拍手分别约 93.96 和 96.15 BPM。生成风格及人耳可辨的 Riff 呼应仍需试听。最终日志在 `system-synth-accepted/` 和 `system-mrt2-openings/`。

编排检查允许当前和弦音及调内音。C 大调 F7 的 E♭ 在该和弦的小节接受，在后续 C 和弦的小节拒绝。保留音符范围、时长、复音重叠、鼓音域及保护声部检查。失败回执包含目标调性、逐小节和弦和实际候选音符。

纯音量与密度指令直接走本地层控制。浏览器后续调整会复用已准备小节的保护声部，已有音符上的音量和密度变化复用原编排。MRT2 直连的浏览器反馈表示模型已接收生成条件，生成完成、等待接入及播放起拍由不同反馈承载。

## F · 连续运行

对照采用 180 BPM，相同冷启动素材及 Chrome Web Audio 时钟。分别保存纯合成、打开调试面板、MRT2 独立播放及交替接入记录。

| 模式 | 第 25 小节 | 第 50 小节 | 第 100 小节 | 第 105 小节 |
| --- | ---: | ---: | ---: | ---: |
| MRT2 原实现，V8 backing storage | 9.81 MB | 16.15 MB | 29.66 MB | 29.22 MB |
| MRT2 分块归档后，V8 backing storage | 0.97 MB | 4.46 MB | 2.63 MB | 7.81 MB |

归档按小节和时间断点封存 PCM 为 Blob。导出由归档构建原始双声道 WAV，保留样本、停奏时刻和播放时间线中的静音间隔。改动前后均完成 105 小节和导出。原实现浏览器报告两次缓冲重接，改动后这一次对照未报告重接。观察值用于验证特定环境的资源改善，更多长时重复运行可判断重接原因。V8 backing storage 与浏览器整体 RSS 是不同指标。

纯合成配对和开启调试面板的测试也完成了 105 小节。交替输出实测从实时伴奏接入约 2.7 秒 MRT2 片段，再回到实时伴奏。105 小节的完整浏览器导出为 138.9 秒，保存在 `after-alternating-export-105/`。浏览器注入不可用模型时，试听显示失败，实时伴奏继续至测试的第 5 小节。最新切换反馈与短版浏览器导出见 `alternating-audio-sample/`。F06 在同一会话接受两段合成哼唱、一次拍手、三次改口与停奏。静音和低幅噪声均未触发旋律。E15 的旧渐强计划被取消，回执只出现在后续保持指令上。当前环境用内置合成作规则路线对照，FluidSynth 性能需要可用的可执行文件与同一 SoundFont。浏览器报告保留累计任务时间、最大并发音频节点和 HTTP 统计。模型资源报告区分进程 CPU、RSS 与浏览器计数。GPU 专用资源和麦克风物理重连还需独立测量。

## 工程选择

| 问题 | 本轮选择与边界 |
| --- | --- |
| Prompt | 使用稳定、简洁的风格底稿。记录实际模型输入并随明确目标更新。短英文、长英文与中文各有独立对照，听感排序由盲听完成 |
| 结构化条件 | 精确要求由显式音符保留。MRT2 先尝试低密度约束，只增加确有必要的旋律、和弦、节奏提示。完整多乐器在统一网格上的过约束由 A–E 消融继续确认 |
| 哼唱 | 用已有录音解码和识别路线处理可验证旋律。提供 Audio 与联合引导实验入口。合成哼唱的近静音结果尚不足以把原始音频设为默认条件 |
| MIDI | 承担精确演奏、可核对的控制条件和降级输出。交替使用完整片段，优先避免完整伴奏同时发声 |
| S0/S1/S2 | 生成试听使用 S0，连续 Jam 在性能允许时使用 S2。S1 可以做有意分段，需为独立片段接缝做额外验证 |
| 连续性与反馈 | 在小节时钟上保留已排程内容，明确区分指令、生成与播放回执。实际增益切换和内存有浏览器对照，主观响应延迟仍用听感标注 |

## 3/4 与 6/8

建议采用四分音符作为内部时间轴单位。3/4 每小节三个四分音符。6/8 每小节也占三个四分音符，但 UI 按符点四分音符报 BPM，以两组八分音符组织重音。互换关系为内部四分音符 BPM 等于 6/8 拍速乘 1.5。

| 模块 | 修改范围 |
| --- | --- |
| InputEvent 与节奏量化 | 由拍号决定网格与重音，更新数拍、录音裁切及边界测试 |
| JamState、BandPlan 与 Agent | 对拍号加版本兼容默认值，按当前拍号校验位置和 Motif 有效期 |
| Pattern、和弦和 MIDI | 新增三拍与复合拍 pattern、MIDI 拍号元数据和旧行为回归 |
| BarClock 与浏览器 | 样本计时、排队窗口、拍点和导出按小节长度计算 |
| MRT2 | 重新投影 25 Hz 帧，按目标拍号生成条件，并测量实际重音 |

这是跨 Contract、Perception、Renderer 和 Runtime 的改动，当前验收维持 4/4。团队确定拍速和兼容策略后，可先实施 BarClock 与 Contract，再分别接入节奏感知、pattern 和浏览器。

## 复跑

先在仓库根目录进入安装了模型依赖的 Python 环境，设置 `PYTHONPATH=src` 和 `MAGENTA_HOME`。浏览器测试通过本机 Chrome，路径可由 `JAMMATE_CHROME` 指定。结果路径使用新目录，便于保留对照。

```bash
python -m jammate.input_server --implementation workspace --port 4204
python -m mrt2_demo.renderer_benchmark --out mrt2_demo/results/renderer-runtime/repeat-model
python -m mrt2_demo.benchmark_system --url http://127.0.0.1:4204 --out mrt2_demo/results/renderer-runtime/repeat-system
python -m mrt2_demo.benchmark_system --url http://127.0.0.1:4204 --out mrt2_demo/results/renderer-runtime/repeat-ablation --ablation
node mrt2_demo/benchmark_browser.mjs http://127.0.0.1:4204 mrt2_demo/results/renderer-runtime/repeat-long mrt2_direct 105 closed
python -m pytest tests mrt2_demo
node mrt2_demo/test-web-recording.mjs
```

`renderer_cases.json` 保存固定输入。生成结果与原始日志在本地 `mrt2_demo/results/renderer-runtime/`，其中包含失败、跳过及待听感评分项目。授权真人素材可通过 `--human` 传给实验脚本，联合对照可同时传入同一旋律的 `--reference-midi`。原文件应由提供者保管。浏览器可通过 `JAMMATE_BENCH_UPLOAD` 测试上传，通过 `JAMMATE_BENCH_SAVE_WAV=1` 保存实际导出产物。
