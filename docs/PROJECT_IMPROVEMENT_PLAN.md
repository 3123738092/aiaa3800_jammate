## 3. P0：本轮已完成的稳定性修复

- 失败后保留当前输入，允许新 plan_id 重规划；重复 event_id 不会重复应用。
- 检查所有 Renderer 的 ack 返回值，拒绝假成功；目录冲突不取消其他正在执行的计划。
- 日志异常与执行状态分离；提交后持久化异常作为 warning 单独报告。
- 模型使用有限读取视图与同一组 schema ID；完整当前输入不被静默裁剪。
- 请求预算包含 system、schema、历史与修正消息；历史快照不再重复持有完整音乐库。
- 增加状态/回执故障注入、300 轮测试及实际 26 轮对话验证。

维护要求：出现 fallback、unresolved 或 persistence warning 时，演示界面要明确显示；不能只显示“已完成”。

## 4. P1-A：输入轮次与时间协议

建议负责人：Wyman + Wenhan/输入负责人。

交付物：一份 `InputBatch`/完成信号约定和模拟输入集。保留现有 InputEvent，在聚合层明确：

- 本轮采集窗口/关联 ID，哪些已完成输入可以一起决策。
- 统一 session 时钟、录音原点、原音频 duration 与识别完成时间。不能用识别完成时间冒充录音时间。
- ASR partial 不触发正式决策；明确 final、取消、无有效拍点、无音符和用户仍在发声等情况。
- 慢识别结果是补充当前轮、形成下一轮，还是仅保存证据；采用有上限的等待时间。

当前 StateManager 按全局 ended_at watermark 丢弃旧结果，不能自动理解“这份慢哼唱其实和刚才文本是一轮”。因此上游需要显式聚合，不能只根据网络到达顺序拼接。

验收：文本/节奏/哼唱以不同完成顺序重放；同组输入不漏模态、不重复执行；迟到结果按约定处理；停止与用户活动信号不被慢识别阻塞。至少覆盖重复发送、不同内容复用同 ID、取消采集和空结果。

## 5. P1-B：异步决策与 Kevin 实时执行

建议负责人：Wyman 负责决策协调与状态，Kevin 负责播放队列和音频输出，共同定义回执。

### 决策任务

- 主会话保持单一状态写入者；输入队列和待决策任务有容量上限。
- 同一轮只接受一个有效结果。新输入/用户停止能使旧结果过期，即使旧网络请求后来返回也不能生效。
- 截止时间由可用播放边界计算，模型修正和网络重试共享同一个总预算。
- 超时继续当前合法伴奏，并标记要求未兑现；禁止把 hold 记成用户要求成功执行。
- 不把 20 秒网络超时、模型推理或 FluidSynth 导出放进音频回调。

验收：人为延迟 Provider、乱序完成、连续新输入和停止；旧结果全部被拒绝，版本不倒退，状态效果不重复；队列不会无限积压。

### 播放时钟与回执

建议增加明确的 `prepared / scheduled / playback_started / playback_completed` 回执阶段：

- prepared 只表示音符/音频已准备，不更新“已经生效”的音乐状态。
- scheduled 记录预定边界；仍可按规则取消尚未播放的内容。
- 起拍时提交语义效果，transport 由实际播放端推进。
- completed 释放/核验活跃音符，并记录实际播放反馈。

这是下一阶段协议，需要实现后才能声称支持。当前 offline acknowledge 会推进到片段末尾，不可直接当现场播放回执使用。

lookahead 根据决策与准备耗时分布、当前 BPM 和设备缓冲计算，不能假设“每次一定赶得上下一个小节”。Kevin 原实验的 stop/start 更新会重启时钟，应替换为共享时间轴上的队列更新。

验收：变速、换节奏、移除声部、停止/继续均对齐约定边界；新输入不重启整段时间轴；无遗留 NoteOn、无卡音。先用虚拟时钟测试，再用耳机与回录测量真实延迟；分别报告模型耗时、调度延迟、设备时间和回录时间。

## 6. P1-C：真人输入与哼唱候选参数

建议负责人：输入/哼唱负责人主做，Wyman 提供批次、协议与下游对照。

当前候选为 onsetThreshold=0.5，原值 0.25；关闭 inferOnsets 单独没有改善。候选在 6 个非静音合成样例中通过 5 个，并保留同音重唱；轻声仍未达标。组员交付版默认值保持原样。

建议先采集至少 3 人、每人 4 类录音、每类 3 次，共 36 段：连续长音、重复同音、带休止的短句、轻声/常见环境噪声。记录设备、采样率、是否有耳机、录音距离和音量；不把这些元数据自动当音乐意图。

在调参前分开发集和按人留出的验证集；同一录音上比较原值与候选，保留原始/cleaned JSON 和 MIDI。阈值选定后冻结参数、模型/文件哈希与评测版本。

验收建议：分别报告音符 precision/recall、持续时间误差、重复同音漏检、休止保留；候选的重复同音 recall 不应因拼接而明显下降。合成标准可继续作为回归门槛，真人指标需在看验证集前约定，不能只汇总一个平均分。

## 7. P1-D：持久化、历史归档与重启

建议负责人：Wyman 主做，Kevin 确认哪些回执能证明实际播放。

交付物：会话存储与恢复入口。建议使用本地事务数据库保存事件 ID/内容指纹、已接受批次、计划版本、执行回执及状态检查点；先保证单进程，再考虑分布式。

- 固定大小的热历史/乐句缓存；完整输入和旧音乐材料移到存储层。需要旧材料时按 ID/时间检索，避免用 LLM 重写“记忆”。
- 去重账本不能因清理内存而丢失，不能把重新发送当新输入。
- 写入失败需区分“没有提交”与“提交成功但导出证据不完整”。恢复不能通过 WAV 文件存在就推断曾经播放。
- 进程重启不自动重放未确认音符。先恢复停止状态或建立新的播放 epoch，再由明确操作继续。

验收：在输入登记、计划排队、开始执行、提交状态、写回执等边界强制退出/恢复；同一 event 不重复生效，过期计划不发声。以 1,000 轮及更长运行验证热缓存上限、磁盘增长与恢复耗时。本轮只完成 300 轮进程内测试，尚未完成这项。

## 8. P2：音乐能力和听感

负责人建议：Kevin 主做后端音色/编排，Wyman 负责能力描述与动作契约。

- 优先开放已能执行并验证的乐器 profile、节奏变化与有限动态控制。每项能力进入模型 schema 前先有执行测试。
- 保持“原样回应”与“允许变奏”的边界。MIDI 可逐音符验证；Lyria 等语义音频后端需要独立的能力声明与评价，不继承 MIDI 的精确保留保证。
- 扩展鼓/贝斯/和弦编排时同时做实际音符检查和人工试听，避免 density 数值变化但声音没有变化。
- 建立固定听感对照：同一输入、同一基础状态、同一时长，随机播放次序，记录节奏贴合、回应清晰度与可控性。

## 9. 建议执行顺序与阶段门槛

| 阶段 | 先做的交付 | 完成条件 |
|---|---|---|
| 第一次联调 | P1-A 输入批次协议 + P1-B 回执阶段草案 | 同一份接口样例，输入/Agent/Renderer 均能读写；边界不靠口头假设 |
| 下一次实现迭代 | 异步决策 + 虚拟 transport + 取消/截止时间 | 故障注入、乱序结果和停止测试通过，音频回调不等待网络 |
| 并行输入验证 | 真人录音与哼唱候选对照 | 冻结验证集；报告按人/条件的失败，不把合成改善当真人证明 |
| 持续运行迭代 | 事务存储、归档、重启恢复 | 1,000 轮缓存不持续膨胀，重启不重复应用或发声 |
| 联合验收 | 真实声卡、多输入、连续播放 | 约定时长的实际演奏，统计延迟、过期计划、卡音、降级和主观听感 |

统一通过条件：契约合法、状态正确、实际音符/音频正确分别计分；fallback、取消、过期、写入 warning 都进入报告。受控测试、合成音频、真实模型调用与真人现场测试分别标记，不混成一个“总体成功率”。
