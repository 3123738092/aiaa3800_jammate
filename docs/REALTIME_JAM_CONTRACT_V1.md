# JamMate 实时调度接口 v1

2026-11-19。先验收一个最小闭环。伴奏已经在演奏，用户说「鼓太满了，留点空间」，输入进入现有 Agent。鼓在实际可调度的小节减少音符，速度、贝斯、键盘保持。三项接口服务于 SPEC 第 4 节的连续互动，由 Wyman 的状态管理与 Kevin 的播放端共同使用。[SPEC 第 4 节](integration/SPEC.md#4-human--ai-jam-logic) · [实时集成计划](PROJECT_IMPROVEMENT_PLAN.md#5-p1-b异步决策与-kevin-实时执行)

## 首版取值

| 参数 | 初值 | 理由 |
| --- | ---: | --- |
| 可生效位置 | 小节第一拍，`beat=0` | 与已有小节时钟和精确音符编排对齐，减少小节中途替换的边界情况 |
| 入队保护余量 | 200 ms | 在起拍前留出固定缓冲。使用真实播放端接入后用设备和缓冲数据校准 |
| 音符准备预算 | 350 ms | 预留给编排校验、音符生成和交接。当前原型仅准备符号音符，真实后端的准备耗时另测 |
| 决策可选位置 | 本轮开始时最早的 3 个可入队小节 | 给慢模型机会，同时给每条反馈设明确的最晚生效位置 |
| 决策和截止时间单位 | 同一 playback sample 域的整数采样位置 | Runtime 先统一音频时钟，调用者再按采样率换算剩余预算 |

96 BPM 的 4/4 小节为 2.5 秒。本项目现有 Mini 与 Luna 的 Agent 阶段中位数约为 3.48 秒和 3.65 秒，因此排程覆盖多个小节。相同的四小节简化鼓计划在本机做了 100 次纯准备测量，p50 约 1.06 ms，p95 约 1.38 ms。该测量包含本地校验和准备音符，设备缓冲、网络和音频生成留待真实联调度量。[文字 Agent 耗时基准](TEXT_AGENT_BENCHMARK.md#对照结果)

## 接口

### 1. 查询最早可入队小节

`schedule_window() -> tuple[ScheduleSlot, ...]` 从当前播放位置按时间顺序给出候选位置。

- `bar` 是从 0 开始的小节号。
- `start_sample` 是该小节第一拍在同一播放时间轴上的采样位置。
- `enqueue_deadline_sample` 和 `decision_deadline_sample` 是该位置的两个截止时间。

Runtime 用 `BarClock` 预报小节起点。查询结果是一份快照，接收实际计划时 Runtime 会再次检查小节、采样位置和剩余时间。用户变速时以新段起拍为分界，之前的小节起点保留，后续小节按新速度计算。[小节时钟](../src/jammate/render/clock.py)

### 2. 绑定和入队

`bind(request, plan) -> BoundDecision` 从请求原有的候选范围内挑选最早来得及准备的小节。准备后使用 `schedule(change) -> bool` 交给 Runtime。两处截止时间均包含等号。

```text
enqueue_deadline  = start_sample - 200 ms 对应的采样数
decision_deadline = enqueue_deadline - 350 ms 对应的采样数
```

以 96 BPM、1 kHz 虚拟时钟为例，小节 1 在采样点 2500 起拍，Agent 结果最晚在 1950 绑定该小节，准备好的计划最晚在 2300 入队。如果 1951 才有决策，用同一份新鲜请求重新选小节 2。整轮最多使用开始时那三个候选的范围，越过最后的决策截止时原伴奏继续。准备工作超过入队截止时间时可以在原范围内重新绑定剩余可用小节。

每份结果都要匹配事件批次、会话和语义状态版本。同一请求只挂一个待播计划。用户给出替代反馈或停止事件时，旧决策和仍可取消的待播计划过期。只读音符预检也会核对已有待播音乐上的保护层。如果后一份计划会暗中覆盖有保护约束的旧渐强或主旋律，该候选会被拒收。

### 3. 起拍确认和音乐状态提交

`PlaybackStarted` 包含 `session_id`、`plan_id`、`bar` 和 `start_sample`。播放侧确认计划的第一帧进入输出后，所有者在同一会话上调用 `StateManager.playback_started()`。真实适配器若能提供 DAC 时间，应把它随回执记录为额外的测量字段。

准备完成、已入队与已播放使用不同语义。状态管理器在实际起拍边界应用计划一次，保存已听到的音乐变化。当前播放位置与已经走完的时长继续由时钟推进。「保持原样」这类无音符改动的计划会保留已经在播放的渐强或旋律。重复起拍回执不会增加一次状态版本或重放动作。虚拟驱动在推进过该小节之前先处理它的起拍确认。离线入口仍使用原来的片段导出回执。[状态提交逻辑](../src/jammate/orchestration/manager.py)

真实播放端可以在借助设备回调确认之前预填缓冲。若音频已经交给设备、无法撤销，适配器必须先确认这次实际起拍，再接受会替换该待播计划的新事件。可撤销的区间才允许换回原伴奏。当前虚拟驱动在起拍之前保留撤销能力，便于先验收逻辑。

## 代码接线

[RealtimeSession](../src/jammate/orchestration/realtime.py) 以一个线程为会话所有者。所有者先调用 `advance_to(0)` 开始基准伴奏，然后处理以下顺序。

1. `observe(events)` 登记输入并给出决策快照与本轮最晚期限。
2. 工作线程运行 `request.decide(agent)`，可以使用现有 RuleAgent 或 LLMAgent。
3. 所有者用 `bind(request, plan)` 绑定生效小节。另一个工作任务运行 `bound.prepare()` 生成该段音符。
4. 所有者调用 `schedule(change)`，得到一份可撤销的待播计划。
5. 虚拟驱动使用 `advance_to(sample)` 推进时间，每轮返回新起拍的小节、实际音符和新计划的起拍事件。

虚拟驱动给出了相邻的小节采样区间和音符。真实接入需要由 Kevin 将相同的查询、入队及回执语义接到可替换播放缓冲和设备时钟。LLM 的工单仍由调用者配置网络预算，当前框架用上述截止时间拒绝迟到结果。停奏后虚拟时钟继续计算静音小节，恢复时可以接在同一时间轴上。

## 验收

```text
python -m pytest tests/test_realtime_session.py -q
```

新增的 13 项用例覆盖截止时间恰好命中、决策来晚时换小节、准备来晚时重新选择、三小节期限到期、过期计划取消、重复回执、LLM 阻塞时继续走拍、停奏与恢复、变速不重置起拍、澄清、保护层及正面反馈对现有渐强的保留。鼓简化用例比较未经修改的贝斯与键盘音符，并用合成器检查相邻小节的采样区间能够连续拼接。[测试代码](../tests/test_realtime_session.py)

实测新增调度用例 **13 项通过**，全仓 **472 项通过**。另外用 96 BPM 的虚拟会话验证一次迟到路径。决策在采样点 2100 返回，第 1 小节按原样演奏，第 2 小节在采样点 5000 起拍时鼓音符从 6 个减至 5 个，贝斯保持 2 个，键盘保持 3 个，相邻小节的采样区间连续。

这一轮验收针对虚拟播放时钟和可控的模型工作线程。声卡实际播放、浏览器连续输出及真实模型的反馈到起拍延迟需要按同一套契约联调后记录。
