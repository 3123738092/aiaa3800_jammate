# 编排最小差异 benchmark

每对输入固定同一份 `JamState`、`BandPlan`、编排 seed 和事件元数据。每次运行都重新生成同一份规则音符，再由选定的编排器处理。A/B 只改一个文本值或一个节奏重音，另保留同输入对照。不同用例可以使用不同声部、BPM、小节数和调度位置。 [基准脚本](../examples/benchmark_arranger.py)

判定读取实际导出的 MIDI。逐声部核对音高、起止 tick、力度和重复数，同时核对速度、小节长度及受保护声部。通过一对用例需要 A 和 B 各自达到预定结果。波形或 MIDI 文件的哈希不同本身无法证明模型做对了所请求的改动。

以下是首次运行的六个单小节鼓组用例。此批固定 100 BPM。

| 用例 | A 与 B 的唯一变化 | 实际 LLM 输出 |
| --- | --- | --- |
| 密度 | 移除 1 个与 2 个指定踩镲音 | 鼓音符 11 → 10。B 额外移除第 2.0 拍的踩镲。 |
| 力度 | 目标音符增加 4 与 8 个 MIDI 力度单位 | 第 1.5 拍踩镲的力度 60 → 64，起止时间相同。 |
| 起音 | 提前与推迟同一鼓音符 0.125 拍 | 起音从第 1.375 拍变为第 1.625 拍，时值与力度相同。 |
| 时值 | 目标音符时值缩到 80% 与 90% | 时值从 0.200 拍变为 0.225 拍，起音与力度相同。 |
| 保护约束 | 要求调整受保护的键盘力度 4 与 8 | 两次都返回空编辑，所有声部与规则基准一致。 |
| 相同输入 | 重复同一条保持指令 | 两次都返回空编辑，所有声部与规则基准一致。 |

2026-11-18 实测使用 `gpt-5.4-mini-2026-03-17`，12 次请求全部通过校验。6 对 MIDI 输出均符合预期，4 对目标音符发生预期变化，2 对对照保持一致。6 对均保留贝斯和键盘的实际音符，并维持此片段原本没有主旋律音符的状态。单次模型处理耗时 1.95–3.47 秒，中位数 2.34 秒。

同一固定计划下，规则基准的 6 对结果均一致。这验证了文字微调在 LLM 编排阶段产生了预期的音符差异。规则 Agent 独立选择不同计划时，规则编排也可以改变输出。首次真实实验每个变体执行一次。

## 扩展批次

保留首批六组，新增七组。每组 A/B 独立执行两次，共 26 对和 52 个变体。

| 新用例 | A 与 B 的唯一变化 | 判定 |
| --- | --- | --- |
| `bass_velocity` | 贝斯力度减 2 或减 4 | 只调整指定贝斯音符，保留附带的主旋律及其余声部 |
| `keys_chord_gate` | 和弦时值缩到 90% 或 95% | 整组和弦音一致缩短，起音和力度保持 |
| `segment_boundary` | 第 0 拍鼓点提前或推迟 0.125 拍 | 提前会越过片段开头，应保留原位。推迟时只动指定音符组 |
| `protected_groove` | 鼓点提前或推迟 | 有 `preserve: groove` 时两次都保持原位 |
| `second_bar` | 贝斯力度减 3 或减 4 | 112 BPM，从会话第 5 小节开始。只改片段第二小节，第一小节全保持 |
| `rhythm_anchor` | 鼓点提前或推迟 | 已采用用户节奏时，两次都保留其拍点 |
| `input_accent` | 节奏事件的第二个重音 0.54 或 0.56 | 文字完全一致。按固定提示将输入重音分别换算成第 1 拍鼓组力度 +4 或 +6 |

严格模式下，模型返回非法编辑、API 失败或未生成 MIDI，都记为该变体未达预期。无变化对照也需要实际生成 MIDI 并比对，不能用空产物凑通过数。每一对分别报告变化方向、两份 MIDI 是否精确、非目标声部是否保持，以及同一变体跨重复是否生成字节一致的 MIDI。

扩展批次实测使用 `gpt-5.4-mini-2026-03-17`。52 次真实请求有 51 次通过校验，**25/26 对的两个 MIDI 都精确匹配**。18/18 对需要变化的用例精确通过，8 对无变化对照中有 7 对通过。同一 A/B 用例跨重复的两份 MIDI 在 12/13 组中均字节一致。52 次编排耗时中位数为 2.57 秒，范围 1.96–4.33 秒。这些时间取自三组并行执行时的日志。

- 键盘和弦由 3 个音组成。时值由 1.8 拍变为 1.9 拍，三音同步变化。贝斯和键盘用例中附带的两音主旋律均保持。
- `input_accent` 两次回放都得到同样的结果。重音从 0.54 变为 0.56 时，第 1 拍的军鼓和踩镲力度分别从 67/42 变为 69/44，其余音符一致。
- 唯一失败在 `rhythm_anchor` 第二次重复的 A 变体。音符组许可仅有 `velocity`，模型却提出 `shift_steps=-1`。校验器拒绝该回复，严格模式没有写 MIDI。用保存的同一回复验证默认规则回退，生成的 MIDI 与基准字节一致。这次回放单独核证，没有计入真实通过数。
- 脚本模拟 26/26 对精确通过。固定 BandPlan 的规则对照 26/26 对保持相同。扩展报告还复核了请求除声明的字段外一致，以及 51 个实际 MIDI 文件的 SHA-256。

扩展实验的汇总包含逐对评分和按用例统计。这个实验测量固定计划下的音符控制。原始运行目录为本机 `demo_out/arrangement_benchmark_expanded.yB6FzO/`。 [扩展实验报告](../examples/benchmark_evidence/arrangement_benchmark_expanded.yB6FzO/llm/report.json)

在已安装项目的仓库根目录执行。`--out` 使用一个尚不存在的目录。

```bash
python examples/benchmark_arranger.py --mode rule --out demo_out/arrangement_bench_rule
python examples/benchmark_arranger.py --mode mock --require-exact --out demo_out/arrangement_bench_mock
python examples/benchmark_arranger.py --mode llm --repeat 2 --jobs 3 --out demo_out/arrangement_bench_llm
```

真实模式沿用项目的 LLM 配置，也可传入 `--config`。`--case velocity --case timing` 可以只检查指定用例，`--repeat 3` 可以复测同一组 A/B。新版输出的 `fixtures/` 保存各组基准状态、计划和 MIDI，变体目录保存输入事件、输出 MIDI、模型日志和 trace，根目录的 `report.json` 汇总每对结果。首批产物仍保存在本机 `demo_out/arrangement_benchmark_20261118/`。
